# Serverless vs 传统服务器

## Serverless 的问题本质

Vercel Serverless 的核心特征：**每次请求可能启动全新进程，用完就销毁**。

这导致：
- 连接池失效（进程活不长，池子建不起来）
- 每次冷启动都有初始化开销
- 不能依赖进程内状态

这些问题不是 Neon 造成的，而是 Serverless 模式本身的特性。Neon HTTP 是在这个约束下的解决方案。

## 生产环境的选择

大部分跑大规模业务的公司，**基本都是传统服务器 + TCP 连接**。

原因：TCP 更快、更稳定、更可控。

### Serverless 适合的场景

| 场景 | 选择 | 原因 |
|---|---|---|
| 公司核心业务（交易、订单、支付） | 传统服务器 | 性能敏感，必须可控 |
| 内部工具、运营后台 | 都行 | 流量小，无所谓 |
| 个人项目、创业 MVP | Serverless | 快速上线，不用管运维 |
| BFF 层（Backend for Frontend） | Serverless | 只做数据聚合，不是核心逻辑 |
| API 网关、定时任务 | Serverless | 短时运行，按需付费 |

### 公司常见的混合架构

```
用户请求
  ↓
Vercel / CDN（Serverless）
  ↓ 静态页面 + 简单数据查询
  ↓
核心业务 API（传统服务器集群，TCP 连数据库）
  ↓
Postgres / MySQL（数据库）
```

Vercel 负责：页面渲染、简单数据读取、静态资源
传统服务器负责：核心业务逻辑、交易、复杂查询

大部分公司不会只选一个，而是各取所长。

## 如何理解技术选型

| | 传统服务器 | Serverless |
|---|---|---|
| 上手门槛 | 高，要懂运维 | 低，写代码就行 |
| 性能上限 | 高 | 有天花板 |
| 运维成本 | 高，要自己管 | 零，平台管 |
| 费用模型 | 固定（服务器租金） | 按量付费（没人访问就免费） |
| 适合阶段 | 公司长大了、有运维团队 | 个人/小团队/快速验证 |

大部分技术选型不是"哪个更好"，而是"现在什么最适合你"。

学习阶段用 Serverless + Neon 是对的——先跑起来，先做出东西。做到需要性能优化的时候，已经有足够理解去切换方案。
