# Serverless 颠覆传统后端概念（提前预告）

## 根本冲突

传统后端假设：**有一个一直在跑的进程**。Serverless 没有。

## 传统概念在 Serverless 下的崩塌

| 传统概念 | 传统做法 | Serverless 下的崩塌点 |
|---|---|---|
| **数据库连接池** | 进程启动时建池，复用到死 | 进程随时生灭，池不复存在 → 连接数爆炸 |
| **后台任务** | 起 worker 进程，跑完就跑完 | 没有长期进程 → 函数超时（Vercel 最多 300s）任务就断了 |
| **定时任务（Cron）** | 服务器上 `cron -e` 注册，到点就跑 | 没有服务器 → 谁来触发？ |
| **长连接（WebSocket/SSE）** | 进程活着，连接就在 | 函数跑完就销毁 → 连接断了 |
| **内存状态** | 进程内存里缓存、session | 函数冷启动 → 内存空了 → 缓存全丢 |
| **流式响应** | 拿到数据慢慢发 | 函数有超时限制 → 必须用特殊模式保持"活着" |

## 后续模块的应对方式

### Inngest（M3）— 解决后台任务 + 定时任务

- 传统：写个 worker 进程，`while true` 循环拉任务
- Serverless：Inngest 帮你管"任务队列 + 重试 + 超时"，你的函数只管处理单步逻辑
- 关键转变：**从"我跑一个长期进程"变成"我注册一堆单步函数，框架帮我调度"**

### AI SDK / Streaming（M2）— 解决长耗时响应

- 传统：请求 → 等模型回复（可能 30 秒）→ 一次性返回
- Serverless：等 30 秒函数就超时了
- 解法：用 Streaming（SSE）一边生成一边推送给客户端，函数"一直在输出"就不会被判定为超时
- 关键转变：**从"等完再返回"变成"边产边推"**

### Streaming / SSE（M2 W5-6）— 解决长连接

- 传统：WebSocket，进程和客户端保持双向通道
- Serverless：函数跑完就没了，WebSocket 不可能
- 解法：SSE（单向流）+ 客户端重连机制，每次函数激活推一批数据
- 关键转变：**从"双向长连接"变成"多次短连接拼成流"**

## 一句话

传统后端的核心假设是**进程活着**，所有设计都基于这个前提。Serverless 把这个假设抽掉了，所以每个传统概念都要重新想一遍"没有长期进程怎么实现"。不是概念错了，是运行环境变了。
