# Neon Serverless Driver 底层优化：从 9 轮到 4 轮

> 来源：Neon 官方文档 [Serverless Driver Overview](https://neon.tech/docs/serverless/serverless-driver) + 创始人博客 [Quicker serverless Postgres connections](https://neon.tech/blog/quicker-serverless-postgres)

## 问题：为什么连个数据库要 9 步？

Serverless 环境每次请求都要**新建**数据库连接（无法复用连接池），所以建连速度就是性能瓶颈。初始连接需要 **9 次网络往返（round-trip）**，如果客户端在欧洲、数据库在美西，一次 round-trip 要 100ms+，9 次 = **超过 1 秒**。

### 9 步分别在做什么

```
第 1 步  TCP 握手（1 轮）
         客户端 → "你好，能建立连接吗？"
         服务端 → "可以"
         客户端 → "好，连上了"
         所有网络通信的前提，就像拨通电话。

第 2 步  WebSocket 握手（1 轮）
         客户端 → "我要在这个 TCP 连接上用 WebSocket 协议说话"
         Serverless 环境不支持裸 TCP，只能用 WebSocket 代替。
         这步是 WebSocket 相比裸 TCP 多出来的唯一开销。

第 3 步  SSLRequest 问询（1 轮）
         客户端 → "你支持 TLS 加密吗？"（发送 magic number 0x04d2162f）
         服务端 → "S"(支持) 或 "N"(不支持)
         注意：这步只是"问"，还没开始加密。

第 4-5 步  TLS 1.2 握手（2 轮）
         双方协商加密算法、交换密钥、验证身份。
         TLS 1.2 需要两个来回才能完成。

第 6-8 步  Postgres 认证 - SCRAM-SHA-256（3 轮）
         第 6 步：客户端 "我是 user123" → 服务端 "请用 SCRAM 证明你是 user123，这是挑战值"
         第 7 步：客户端 做几千次哈希运算 → "这是我的计算结果" → 服务端 "验证通过"
         第 8 步：服务端 "你可以发查询了"
         SCRAM 是 challenge-response 机制，见下文详解。

第 9 步  查询 + 返回结果（1 轮）
         客户端 → "SELECT * FROM users"
         服务端 → 返回结果
         唯一真正干活的步骤。
```

**9 步里只有最后 1 步在干正事，前面 8 步全是在"建立安全通道"和"证明你是谁"。**

## TLS 是什么？TLS 1.2 vs 1.3

### TLS 解决什么问题

TLS = Transport Layer Security（传输层安全协议）。

你和数据库之间的网络路上可能有黑客在偷听（中间人攻击）。TLS 把所有通信内容**加密**，偷听者只能看到乱码。日常浏览 `https://` 网站，那个 "s" 就是 TLS 在工作（浏览器地址栏的锁图标）。

### TLS 握手在做什么

握手 = 双方在不安全的网络上，协商出一个**只有双方知道的加密密钥**。

方法是**非对称加密**（如 ECDHE）：双方各生成一半密钥材料，用数学方法合并成完整密钥，即使被人截获也无法还原。

### TLS 1.2 需要两轮

```
第 1 轮：
  客户端 → "我支持这些加密算法，这是我的半份密钥材料"

第 2 轮：
  服务端 → "我们用这个算法，这是我的半份密钥材料 + 我的证书"
  客户端 → "好的，密钥算好了，从现在开始加密通信"
```

### TLS 1.3 只需要一轮

TLS 1.3 的优化：**客户端不再"询问"服务端支持什么，而是直接"猜"**。

```
第 1 轮（唯一一轮）：
  客户端 → "我猜你支持这些现代算法（大概率猜对），这是我的半份密钥材料"
  服务端 → "猜对了！这是我的半份，密钥建立完毕"
```

为什么敢猜？TLS 1.3 砍掉了所有老旧的不安全算法，剩下的就那么几种，猜对的概率接近 100%。如果真的猜错了（极罕见），就回退重试。

**省 1 轮 round-trip = 省一次跨国网络往返，可能就是 100ms。**

### 优化效果：9 → 8

## "加密下沉到 WebSocket"是什么意思

### 原来的架构（加密做两次）

```
客户端 ——[wss: TLS 加密]——> WebSocket 代理 ——[TLS 加密]——> Postgres
```

有**两层加密**：
- 外层：`wss://`（WebSocket Secure）本身就是 TLS 加密的
- 内层：Postgres 自己又在里面再做一次 TLS

像把信装进一个保险箱，又把保险箱装进另一个保险箱——外层已经够安全了，里面那个多余。

### SSLRequest 这步就是为内层加密服务的

在 Postgres 建立内层 TLS 之前，客户端要先问一句：

```
客户端 → Postgres：0x04d2162f（一个 magic number）
Postgres → 客户端：0x53（'S'，支持 TLS）或 0x4e（'N'，不支持）
```

一问一答 = 一个 round-trip。对 Neon 来说答案永远是 S，所以这轮**完全是浪费**。

### "下沉"后的架构

```
客户端 ——[wss: TLS 加密]——> WebSocket 代理 ——[明文]——> Postgres
```

- Postgres 不再做 TLS，由外层 `wss://` 承担加密
- 既然 Postgres 不做 TLS，就不用问"你支持 TLS 吗"——SSLRequest 直接消失
- **安全性不变**：数据在公网上传输时仍然加密，只是加密责任从上层（Postgres 协议层）移到下层（WebSocket 传输层）

**"下沉"= 把加密的责任从上层移到下层，省掉一个多余的协商步骤。**

### 优化效果：8 → 7

## SCRAM 是什么？为什么一开始用它？为什么后来不用了？

### SCRAM 解决什么问题

SCRAM = Salted Challenge Response Authentication Mechanism

核心目标：**怎么证明你知道密码，但又不把密码本身发出去？**

### 为什么不能直接发密码？

即使有 TLS 加密，直接发密码仍有风险：
1. 服务端如果存明文密码，数据库泄露 = 所有人密码泄露
2. 客户端直接发密码，服务端必须存明文（或等价物）才能验证

### SCRAM 怎么工作的（3 轮）

```
第 1 轮：客户端告诉服务端 "我是 user123，我想认证"
第 2 轮：服务端返回一个随机挑战值（salt + iteration count）
         客户端用 挑战值 + 自己的密码，做几千次 SHA-256 哈希运算，返回计算结果
第 3 轮：服务端验证结果是否正确
```

密码本身从未在网络上传输。

### SCRAM 的三大优势

1. **密码不在网络上传输** — 即使 TLS 被攻破，攻击者拿到的也不是密码
2. **服务端只存 salted hash** — 数据库泄露也不暴露原始密码
3. **故意算得很慢** — 几千次 SHA-256 迭代，暴力破解成本极高
   - 攻击者每猜一个密码要花 ~100ms CPU
   - 猜 1 万个 ≈ 16 分钟，猜 100 万个 ≈ 27 小时

### 为什么 SCRAM 的优势在 Serverless 里变成了劣势

关键矛盾：

| | 传统服务器 | Serverless（CF Workers） |
|---|---|---|
| CPU 时间 | 不限 | 免费版 10ms，付费版 50ms |
| SCRAM 需求 | ~100ms CPU | 远超预算 |
| 连接复用 | 建一次连用很久 | 每次请求都要新建连接 |

SCRAM **故意设计的"慢"**，在 Serverless 里变成根本跑不完。CPU 预算 10ms，光认证就要 100ms，直接超时。

### 为什么换成随机密码就安全了

SCRAM 的"慢"是为了防**字典攻击**——攻击者用常见密码（password123、admin888）逐一尝试。但字典攻击的前提是：**密码是人类选的，有规律可猜**。

Neon 的密码是**机器生成的随机字符串**（如 `a7Kx9mP2qR5nB8wL`）：
- 搜索空间巨大（16 位随机字符 ≈ 2^128 种可能）
- 字典攻击根本不适用——没有字典能覆盖
- 不需要 SCRAM 的"慢"来保护，暴力破解在数学上就不可行

### 为什么一开始不用简单密码认证

不是"没想到"，而是：
1. **SCRAM 是 Postgres 的标准认证方式**，开箱即用，兼容性最好
2. 后来发现 Serverless 场景下 CPU 预算根本不够用
3. 经过安全分析，确认"随机密码 + 简单认证 + TLS 加密传输"的组合足够安全
4. Neon 只生成随机密码、不支持用户自设密码，所以字典攻击的威胁不存在

**SCRAM 用"算得慢"防暴力破解，Neon 用"密码本身够随机"达到同样目的，省掉了慢的计算。**

### 优化效果：7 → 6

## 消息流水线（Pipelining）：6 → 4

去掉 SCRAM 后，Postgres 交互还剩 3 轮：
1. 客户端发 startup → Postgres 要求密码认证
2. 客户端发密码 → Postgres 说 OK
3. 客户端发查询 → Postgres 返回结果

**关键洞察**：只有第 3 步（查询 + 结果）需要等回复，前两步不需要。

Pipelining = 把这三条消息**一次性发出去**，不等回复：

```
原来（6 轮）：
  TCP + WebSocket + TLS(1轮) + startup/密码/查询 各一等 = 6

Pipelining（4 轮）：
  TCP + WebSocket + TLS + 三条消息打包一次发 = 4
```

### 踩坑：Nagle 算法

Pipelining 在短距离（同机房）反而更慢。原因是 **Nagle 算法**把小包攒着发，导致 pipelined 消息被延迟。

解决：在 WebSocket 代理设置 `TCP_NODELAY`，禁止 Nagle 算法攒包。

## 总结：优化路径

```
9 轮（初始）
 ↓  升级 TLS 1.3（TLS 握手 2 轮 → 1 轮）
8 轮
 ↓  加密下沉到 WebSocket（省掉 SSLRequest 问询）
7 轮
 ↓  SCRAM → 简单密码认证（省掉 challenge-response 往返）
6 轮
 ↓  消息 Pipelining（startup + 密码 + 查询一次发完，省 2 轮）
4 轮（当前）
```

未来展望：QUIC/HTTP/3 可能进一步降到 3 轮甚至 2 轮（QUIC 把 TCP 和 TLS 握手合并成一步）。
